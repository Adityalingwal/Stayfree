## FIX 1 — `WhisperServer` lifecycle state machine overhaul ✅ APPROVED

**File:** `src/main/whisper/server.ts` (only this file; public API — `start()`,
`ensureReady()`, `restart()`, `stop()`, `getStatus()`, `baseUrl` — unchanged, callers
untouched)

**Issue (4 confirmed sub-defects, dono reviewers ne pakde):**

1. **Failed start strands the state.** `doStart()` ke `catch` (server.ts:299-308) mein
   status update NAHI hota — `pollReady()` timeout/spawn-error ke baad status
   `"starting"`/`"restarting"` pe hamesha atka rehta hai. `ensureReady()` (318-349)
   sirf `"unavailable"`/`"stopped"` pe naya start kick karta hai, to stranded state mein
   har dictation poora 4s `READY_TIMEOUT_MS` waste karke fail hoti hai. Failed start ka
   child process bhi zinda reh sakta hai (pollReady timeout != child dead) — use kill
   nahi kiya jata, state file/port clear nahi hote.

2. **Child exit ownership missing.** `handleExit()` (397-412) ko pata nahi kis child ka
   exit aaya — unconditionally `this.child`/`this.port` clear karta hai. `restart()`
   (367-381) SIGKILL bhejta hai aur turant `start()` karta hai; purane child ka async
   exit event naye child ka "unexpected crash" samjha ja sakta hai → naye ka
   handle/port clear, waiters fail, faltu restart schedule.

3. **Circuit breaker kabhi trip nahi hota.** Har successful readiness pe
   `crashTimestamps` poora clear ho jata hai (301-302). Jo binary ready hoke 1s baad
   crash hota hai, wo hamesha crash-count 1 pe wapas aata hai → 0ms backoff, unlimited
   hot-respawn (CPU/Metal/RAM churn). Aur agar breaker trip ho bhi jaye,
   `scheduleCircuitBreakerRetry()` (415-456) sirf EK retry schedule karta hai — wo
   retry fail ho to agla 30s wala kabhi schedule nahi hota.

4. **`intentionalStop` shared boolean race.** `restart()` `intentionalStop=true` set
   karta hai, phir `start()`; agar `start()` kisi in-flight `startPromise` ko
   early-return kare to reset (`=false`) kabhi nahi chalta, `handleExit` bhi flag clear
   nahi karta → agla genuine crash "intentional" samjha ja kar auto-restart swallow.
   Razor-thin ordering pe `status="ready"` + `child=null` bhi ho sakta hai
   (transcriber "no base URL" throw karega).

   **Sub-case (Claude reviewer):** Metal shader cache evict hone pe cold compile
   ~7.5s > pollReady ka 4s → healthy-but-loading server ko `restart()` mid-compile
   SIGKILL karta rahega, kabhi converge nahi. (Rare, but design should tolerate a
   slow-loading child bina use maare — see fix rules below.)

**Fix (design rules — implement exactly these):**

1. **Child generation tracking.** Har spawn ko ek monotonically-increasing generation
   number do (`gen`). `child`, `port`, `intentionalStop`, exit handler — sab us
   generation se bandhe hon (e.g. ek `ActiveChild { gen, proc, port, intentionalStop }`
   object). `handleExit(gen)` sirf tab state mutate kare jab `gen === currentGen` —
   purane children ke exits sirf log hon, ignore hon.
2. **Har failed start transactional ho.** `doStart()` fail ho (spawn error, pollReady
   timeout, bind fail) to: (a) us attempt ka child agar zinda hai to SIGKILL, (b) state
   file + port clear, (c) status ko explicit terminal state pe le jao — crash-class
   failure → `"crashed"` + backoff-scheduled restart; assets missing → `"unavailable"`.
   Kabhi bhi `"starting"` pe mat chhodo.
3. **`ensureReady()` stranded-state-proof ho.** Agar status aisa hai jisme koi
   in-flight attempt actually resolve karne wala nahi hai, to ensureReady ek fresh
   `start()` kick kare (existing "force one clean attempt" semantics ko generalize
   karo) — kabhi bhi aisi wait register na ho jo koi resolve nahi karega.
4. **`restart()` serialize karo.** In-flight `startPromise` ko share mat karo — pehle
   current attempt/child ko settle karo (kill + uska exit consume), phir naya spawn.
   `intentionalStop` per-child hai (rule 1), to reset-leak khatam.
5. **Crash accounting fix.** `crashTimestamps` ko ready hone pe clear MAT karo —
   rolling 60s window naturally purge karti hai; sirf ek "proven stable" interval
   (e.g. ready + 60s bina crash) ke baad clear karo. Breaker trip ke baad har failed
   retry agla 30s retry re-arm kare (loop, single-shot nahi).
6. **Slow-loading child ko maaro mat (shader-compile case).** pollReady timeout pe
   agar child abhi bhi ZINDA hai (exit nahi hua), to use turant kill karne ke bajaye:
   attempt ko fail karo (waiters reject, status `"crashed"`+scheduled retry) LEKIN
   child ko chalne do aur uske liye ek extended grace window rakho (e.g. usi child pe
   background poll continue, max ~15s; ready aa jaye to use adopt karo status
   `"ready"`). Agar 15s tak bhi nahi, tab kill. Ye 7.5s Metal-compile case ko bina
   kill-loop ke converge karne deta hai. (Simple implementation acceptable: ek
   "lateReady adoption" poll on the same generation.)

**Constraints:** Koi naya dependency nahi. Baaki app files touch nahi karni (FIX ke
scope se bahar). Existing log style (`[Whisper] ...`) rakhna. D7 flags/D5 constants
unchanged.

**Verify (static):** `npm run package` + `npm run lint` clean. Code-walk: har failure
path pe status ka terminal transition trace karke likhna (agent apni summary mein
transitions ka table de).

## FIX 3 — Zombie sweep: substring match → exact executable match ✅ APPROVED

**File:** `src/main/whisper/server.ts` (sweep function, ~line 136-176)

**Issue (dono reviewers, confirmed):** Startup zombie sweep PID validate karne ke liye
`ps -p PID -o command=` ka output leta hai aur `cmd.includes(state.executablePath)`
check karta hai (server.ts:158). Ye command-line TEXT substring match hai — wahi
false-positive class jo plan D2 ne explicitly reject ki thi (`pkill -f` reject karne
ki wajah yahi thi). Failure case: purana whisper-server mar chuka, macOS ne wahi PID

risk".

**Fix:** Identity check ko exact-executable comparison banao — `ps -p PID -o comm=`
(ya `command=` ka PEHLA token) ko `serverBin` ke absolute path se **equality** se
compare karo, substring se nahi. Match sirf tab jab process ka executable khud hamara
binary ho. (Optionally aur bhi strict: process ownership/uid check.) Baaki sweep
logic (state file read → validate → SIGKILL → state file delete) unchanged.

**Verify (static):** Code-walk — `tail -f <path>` / `otool -l <path>` jaise commands
ab match NAHI ho sakte; sirf `<path>` khud as argv[0] match ho.

## FIX 4 — Quit-time races: shutdown ke baad naya server spawn ho sakta hai ✅ APPROVED

**Files:** `src/main/whisper/server.ts` (primary; FIX 1 ke saath ek hi overhaul mein
implement karna) + `src/index.ts` before-quit handler (~1429-1464) agar zaroorat pade

**Issue (dono reviewers, confirmed — do windows):**

1. **Quit during in-flight transcription (Codex):** `before-quit` → `stop()` SIGTERM
   bhejta hai child A ko → in-flight `fetch` fail hota hai → `transcriber.ts` ka retry
   path `restart()` call karta hai (transcriber.ts:88-99) → child B spawn ho jata hai
   quit ke baad. `stop()` mein koi flag nahi jo stopping ke dauran `start()`/`restart()`
   ko roke (server.ts:367-381, 460-509). `whisperStopped` already true hai to
   before-quit ka doosra pass B ko band nahi karta. B orphan (113MB) reh jata hai.
2. **Quit during startup (Claude):** `stop()` with `this.child === null` (doStart abhi
   `pickFreePort` ya pre-spawn awaits mein hai) early-return karta hai —
   `intentionalStop` set kiye BINA aur in-flight `doStart` cancel kiye bina
   (server.ts:460-476). `doStart` phir quit ke baad spawn kar deta hai (spawn line 277
   do awaits ke baad aati hai). Orphan.

Mitigation jo already hai: agla launch ka sweep orphan ko reap karta hai (FIX 3 se aur
safe). Lekin plan §5.4 ka "normal quit → `pgrep whisper-server` empty" in windows mein
fail hota hai.

**Fix (design rules):**

1. **Terminal `shuttingDown` state.** `stop()` sabse pehle ek permanent
   `shuttingDown=true` flag set kare (child ho ya na ho, unconditionally). Uske baad:
   - `start()` / `restart()` / `ensureReady()` turant reject karein
     ("server is shutting down") — koi naya spawn kabhi possible nahi.
   - In-flight `doStart` spawn se PEHLE aur spawn ke turant BAAD flag check kare;
     set hai to: pre-spawn → attempt abort; post-spawn → us child ko turant SIGKILL +
     state cleanup. (FIX 1 ke generation-tracking se ye natural hai — attempt apni
     generation ke against flag check karta hai.)
2. **`stop()` current attempt ko settle kare.** Agar `doStart` in-flight hai to stop
   use await/cancel kare (generation mark karke), sirf `this.child` null dekh ke
   early-return NA kare.
3. Transcriber side kisi change ki zaroorat nahi — `restart()` reject karega to
   mapError `ENGINE_UNAVAILABLE`-class error dega, pipeline waise hi surface karti
   hai. (Quit ho raha hai, user ko farak nahi padta.)

**Verify (static):** Code-walk dono windows ka: (a) quit during ASR-retry → restart
reject, koi spawn nahi; (b) quit during startup → doStart abort, spawn nahi hota ya
turant killed. Runtime: Aditya ka Test 3 (normal quit → `pgrep whisper-server` khali)
fixes ke baad.

## FIX 5 — Bind-failure port retry + child-bound readiness ✅ APPROVED

**File:** `src/main/whisper/server.ts` (FIX 1 overhaul ka hissa — same doStart path)

**Issue (dono reviewers, confirmed):**

1. **Spawn-stage port retry missing (plan D2 deviation).** Code ek port probe karta
   hai (server.ts:85-105), release karta hai, ek baar spawn karta hai (264-307).
   Probe-close aur spawn ke beech koi aur process port le sakta hai. Plan D2 ne bola
   tha: "on bind-failure exit, pick another (max ~5 tries)" — ye loop exist nahi
   karta. Abhi bind-fail → child exit → generic crash-restart machinery (jo circuit
   breaker mein crash count karti hai — port collision crash nahi hai, accounting
   pollute hoti hai).
2. **`pollReady()` kisi ka bhi HTTP response accept karta hai (Codex).** Ready-check
   sirf "port pe HTTP response aaya" dekhta hai (397-443 region) — ye nahi ki response
   HAMARE child ka hai. Port-steal case mein: humara child bind-fail se mar chuka,
   occupying service HTTP answer karti hai → hum use "ready" maan lete hain → saari
   `/inference` requests us unrelated service pe jaati hain.

**Fix (design rules):**

1. **Bounded attempt loop:** `doStart()` ke andar probe→spawn→ready ek attempt hai.
   Agar child bind-failure se turant exit kare (spawn ke jaldi baad exit, ready se
   pehle) → naya port pick karo aur immediately retry, max 5 attempts. Ye retries
   circuit-breaker ke `crashTimestamps` mein COUNT NA hon (port collision ≠ crash).
   5 attempts ke baad hi crash-class failure treat karo (FIX 1 rule 2 ka terminal
   transition).
2. **Child-bound readiness:** pollReady apni generation ke child se bandha ho (FIX 1
   rule 1): (a) child exit ho jaye to us attempt ka poll turant fail ho — kisi aur ke
   HTTP response ka wait/accept nahi; (b) response sirf tab "ready" jab current
   generation ka child us waqt zinda ho. (Optional hardening: ready-probe endpoint ka
   response shape sanity-check — whisper-server jaisa dikhta hai ya nahi — lekin
   child-alive check primary hai.)
3. Off-by-one nit isi mein: port range random pick `65535` ko kabhi include nahi
   karta (server.ts:88-90) — `floor(random * (MAX - MIN + 1))` kar dena.

**Verify (static):** Code-walk: (a) simulated bind-fail path → naya port, ≤5 tries,
breaker untouched; (b) child-dead-during-poll → attempt fail, foreign HTTP response
kabhi ready nahi banata.

## FIX 8 — Deadline ke baad stale retry/restart rokna + deadline 20s → 12s ✅ APPROVED

**Files:** `src/main/whisper/transcriber.ts` + `src/index.ts`

**Issue (Codex, confirmed; Claude ne related math-bug pakda):** 20s
processing-deadline expire hone pe sirf `activePipelineId` invalidate hota hai
(src/index.ts:524-545) — underlying kaam cancel NAHI hota. Stale `transcribePcm()`
ka retry path deadline ke BAAD bhi `restart()` call kar sakta hai — matlab purani
(cancelled) dictation naye recording ke dauran server ko SIGKILL/respawn kar sakti
hai. (Claude side-finding: plan D5 ka "13s worst + 7s margin" math bhi galat tha —
asli worst chain ~17s hai; ab irrelevant, kyunki approach hi badal rahi hai.)

**Fix (Option 2 — minimal, approved; full AbortController plumbing streaming phase
mein):**

1. **Cancellation check:** `transcribePcm(pcm16, shouldContinue?: () => boolean)` —
   optional callback. Har retry-decision point pe (attempt fail hone ke baad, restart
   se PEHLE, aur attempt 2 shuru karne se pehle) `shouldContinue()` check karo; false
   → koi restart nahi, koi retry nahi — turant throw (existing mapped error;
   pipeline-side already stale hone par use ignore karti hai). In-flight HTTP request
   apne 4.5s timeout se khud settle hota hai — harmless, use force-abort karne ki
   zaroorat nahi (yahi minimal scope hai).
2. **Call site:** `src/index.ts` mein `transcribePcm(buffer, () => activePipelineId
   === pipelineId)` pass karo.
3. **Deadline reduce:** `PROCESSING_TIMEOUT_MS = 20000` → `12000` (src/index.ts:84).
   Rationale (Aditya-approved): local engine, measured ASR 0.15-1.2s; 12s hung-server
   self-heal chain (attempt1 timeout ~8.5s + instant-SIGKILL restart ~1s + attempt2
   ~1s ≈ 10.5-11s) ko fit karta hai, 20 ka lamba wait khatam. 10s consider hua,
   reject — self-heal window kat jaati thi.
4. Deadline-expiry ka error pill behavior unchanged (already D1-compliant).

**Constraints:** `READY_TIMEOUT_MS`/`ASR_REQUEST_TIMEOUT_MS` unchanged. Signature
change backward-safe (optional param). Koi AbortController plumbing nahi (deferred).

**Verify (static):** Code-walk: deadline fire → stale transcriber ka agla decision
point → no restart, no retry, clean throw. Happy path unchanged. 12s constant ek hi
jagah.

## FIX 9 — setup-whisper.sh: false-pass smoke, non-atomic install, fragile rpath ✅ APPROVED

**File:** `scripts/setup-whisper.sh` (self-contained; app code untouched)

**Issues (confirmed):**

- **(a) Smoke false-pass — fixed port 58199 (dono reviewers).** Smoke test fixed port

  karta hai, curl occupying service ko hit karta hai, script "Setup complete" print
  kar deti hai — install actually broken. `SMOKE_PID` zinda hai ya nahi, koi check
  nahi. (Bonus mismatch: echo "/inference" bolta hai, actual sirf GET `/` hota hai.)
- **(b) Non-transactional install (Codex).** Files seedha live destination
  (`~/Library/Application Support/StayFree/whisper/`) pe copy hoti hain. Interrupted/
  disk-full copy pehle ka WORKING install destroy kar deta hai. Size-completeness
  check sirf binary+model pe hai, dylibs pe nahi. Unmatched dylib glob bhi confusing
  `cp` error deta hai, clean check nahi (line ~55-56).
- **(c) Fragile rpath patch (Claude).** `install_name_tool -rpath "$WHISPER_CPP_SRC"
  "@loader_path"` (line ~78) assume karta hai binary ka embedded LC_RPATH exactly
  `$WHISPER_CPP_SRC` hai. Binary kahin aur build hua ho to tool error → `set -e` se
  cryptic abort.

**Fix (design rules):**

1. **Staged atomic install:** Sab kuch ek temp sibling dir mein karo (same volume,
   e.g. `whisper.staging.$$/`): copy binary+dylibs+model → completeness check HAR
   required file pe (dylibs included; missing-glob pe clean error message) → chmod →
   rpath patch → codesign → smoke test STAGING binary pe. Sab pass hone ke baad hi
   atomic swap: purana dir `mv` to backup/aside, staging `mv` to final (ya
   rename-swap), phir aside cleanup. Fail kahin bhi ho → staging delete, existing
   install untouched.
2. **Smoke hardening:** Fixed 58199 hatao — free ephemeral port dhoondo (app jaisi
   probe approach ya loop-try). Success ke liye: (i) `kill -0 $SMOKE_PID` — spawned
   server ZINDA hai, (ii) usi port se HTTP response. Dono chahiye. Echo message ko
   actual test se match karao (GET `/` readiness). (Actual /inference POST optional —
   agar trivially possible ho to better, warna readiness kaafi hai per D9.5.)
3. **Robust rpath:** Binary ka ASLI LC_RPATH `otool -l` se read karo aur use replace
   karo; ya `-delete_rpath` all-absolute-rpaths + `-add_rpath @loader_path` sequence.
   Guess-based `-rpath old new` nahi. Patch ke baad wahi existing `otool -l`
   verification + codesign.

**Verify:** `bash -n` clean; dry-read walkthrough of failure points (occupied port,
missing dylib, interrupted copy) — har ek pe script FAIL kare with clear message,
existing install intact rahe. (Real fresh-machine run = packaging phase.)
